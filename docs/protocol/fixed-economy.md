# Fixed-reward economy protocol v1

Local prototype only. Rust models in contracts/economy/src/model.rs and TypeScript models/encoder in packages/shared/src are authoritative implementation definitions. Command amounts, fees, versions, timestamps and seeds are unsigned integer decimal strings; never JS numbers. The encoder is server-side (Node crypto), not a browser signing implementation.

Command Borsh layout: actor string, Action enum. Enum indices: Debit0, Publish1, Admit2, Settle3, Void4, FinalizeClose5. Rust declaration order defines struct field order. UTF-8 strings/vectors use u32 little-endian lengths; quantities use u64 little-endian; option rewards use 0/1 tag and catalog index. Catalog order: club, sword, armor, herb, iron, flask, tonic, fineTonic. Hash is SHA256 of those bytes. Sandbox tests compare encodings/hashes and Rust JSON roundtrips, including max u64 and Unicode. Unknown/unimplemented command variants reject at deserialization; they do not create an Applied receipt.

Every execute command requires the initialized operator as predecessor. Actor is a custodial demo profile selected by the operator; this does not authenticate a human wallet. Same op ID/same hash returns the stored immutable result. Different hash panics without changes. Application validation rejects store Rejected receipts. Capacity/envelope/authorization failures panic without an operation receipt; the future outbox must reconcile final transaction status before classifying those failures. Missing operation is not a rejection.

Validation is staged on a bounded state clone; only successful commands commit economic mutations. Rejected receipt insertion is intentional, not an economic effect. Limits: 32 editions, 64 lifetime run records, 256 receipts, 128 funded item IDs per publication, 16 sockets, 32KiB execution input, 64-byte operation IDs. Retained history is not pruned. Each active run reserves one future terminal receipt and each open edition reserves one closure receipt. New commands/rejections cannot consume that headroom. Admission/publication must fit their new liabilities; capacity exhaustion blocks new work, not valid terminal cleanup. Storage is funded by the local contract account; real deployment storage budget is not yet prepared.

Prototype seed allocation (once per contract): maker100 credits, buyer/p2/p3/p4/p5 each10; bank0. Five owned clubs, three maker swords, six maker tonics. These are disclosed initial test grants, not maker purchases or organic demand. No runtime mint entrypoint. Monotonic edition/run IDs; seeded item IDs never reused.

Publication: 2–4 existing room-module IDs, repeated modules allowed; cellar/gauntlet only until M25 adds templates. Four numbered socket slots per module, unique room/slot pairs, unique socket IDs; geometry/editor coupling comes with M25–27. Rules v1, 15-minute run duration, four concurrent runs, finite maker tags, maximum one-day opening. Placement costs are prototype defaults: publication2, pursuer2, charger3, trap1, reward socket1. Fixed stock must cover at least one entire advertised bundle; extra complete or partial reserve stock may remain but cannot create a partial admission. Intentional no-reward editions have no reward sockets/funding. Fixed-only now: random stock/refresh are M22/M23, not implemented.

Admission: operator seed retained, fixed items selected deterministically by ID; all reward sockets must fill in one transaction. Exact quote version/fee, opening interval, self-entry, per-profile1 and edition4 caps checked. Loadout belongs to player, is unique, fits six bag slots plus at most one weapon/armor slot. Fee goes into the run, not maker's spendable credits. Receipt contains immutable run assignments and deadline from contract block time.

Settlement: exact six-way origin partition, valid current source locations, potions-only consumption, and legal outcome destinations. Extraction's declared carried-dungeon set must exactly equal extracted items; the operator remains trusted about gameplay acquisition/consumption. Contract cannot prove combat. A late Extracted/void command is deliberately allowed: an outcome may have been durably decided before deadline and submitted after an outage. Only Expired checks its earliest allowed time; the forthcoming server action/deadline worker must prevent gameplay after deadline. Rejection solely on submission time would wrongly confiscate legitimately finished runs. Loss sends town goods to bank; surviving dungeon rewards return to their edition. Void refunds fee and surviving town goods, retains consumption, and records reason. Both extraction and loss pay the original escrow fee to maker. Expired checks contract deadline; every terminal operation remains allowed after edition cutoff. Replayed op is stable; fresh second settlement rejects.

Closure: maker actor only, cutoff reached, no active run reservations; residual edition stock goes to bank once. No maker refund, no early confiscation. Server-side unresolved outbox operations and crash recovery are still M14–20; do not infer them from contract atomicity.

Debit enum index0 is a tombstone that always returns DeprecatedSmokeCommand; preserving the index avoids shifting every later Borsh tag. The legacy debit() wrapper was removed. The original M06 proof remains historical evidence, while current smoke tests prove init-once and stable rejected receipts. Initialization is private to the contract account. Local browser practice remains independent: these contract operations are not yet called by the UI.
